## Context

The API base and the LLM provider layer are in place (archived changes `add-api-project-base` and `add-llm-providers`):
- Express 5 with controller → service → repository layering and manual DI in `Container`. Controllers implement `Controller { basePath, routes() }` and are mounted under `/api` behind the session, CSRF and rate-limit middleware.
- `ConfigLoader` merges `config/app.config.json` with the environment, validates it with `AppConfigSchema` (strict zod objects, cross-field rules in `superRefine`) and deep-freezes it. `test/support/testConfig.ts` builds the same shape by hand for tests.
- `Database` opens SQLite through Drizzle and runs migrations from `apps/api/src/db/migrations` on construction (`foreign_keys = ON`). The only table is `players`; `PlayerRepository` is the reference repository style (synchronous Drizzle calls, plain domain objects out).
- `DecisionProvider.decide()` returns `DecisionResult { provider, model, answers, usage, latencyMs }`. Answers are `choice` / `score` (with `confidence`) or `noul` (`probability` only). Provider errors are `AppError`s with a `code` (`PROVIDER_UNAVAILABLE`, `PROVIDER_BAD_RESPONSE`).
- `packages/shared` exports zod schemas plus inferred types and is consumed from source in development (`development` export condition).

Motivation and scope: see `proposal.md`. Required behavior: see the four delta specs.

## Goals / Non-Goals

**Goals:**
- Contracts the game engine and the web UI can share without either one redefining them.
- Hidden investor information is structurally impossible to return: it lives in API-only types, and public DTOs are built from allowlists and validated by strict schemas.
- Everything is testable with `:memory:` SQLite and the fake decision provider.

**Non-Goals:**
- Any game flow: no `/api/games` endpoints, no opening offer, no turn processing. The game DTOs are defined but not served.
- Using the confidence gate or the decision logger from real game code. They are built, tested and wired in `Container`, and the investor-brain change calls them.
- Retention or cleanup of old sessions and decision logs.

## Decisions

### 1. Module layout
```
packages/shared/src/game/
  Money.ts               MoneySchema, EquityPercentSchema
  ValuationCalculator.ts pure math (no zod dependency on DTOs)
  GameSchemas.ts         Offer, StartupPitch, ChatMessage, PlayerOption, GameStatus, GamePhase, InvestorMeters
  GameDtos.ts            InvestorPersonaDto, PersonaListDto, GameSessionDto, TurnResultDto, DecisionInsightsDto,
                         CreateGameRequest, PlayTurnRequest
apps/api/src/
  db/schema.ts           + gameSessions, messages, offers, decisionLogs
  db/migrations/0001_*   generated by drizzle-kit
  game/InvestorState.ts  API-only zod schema + type for the hidden investor state
  repositories/          GameSessionRepository, MessageRepository, OfferRepository, DecisionLogRepository
  llm/decision/          ConfidenceGate.ts, DecisionLogger.ts
  personas/              PersonaDefinitionSchema.ts, InvestorPersona.ts, PersonaCatalog.ts, personaDefinitions.ts,
                         PersonaDefinitionError.ts
  http/controllers/      PersonaController.ts
```
`ValuationCalculator` sits in its own file with no imports from the DTO files, so `GameSchemas.ts` can use it in the `Offer` refinement without a cycle.

### 2. Valuation semantics
`impliedValuation` on an offer is the **post-money** valuation (investment ÷ equity share), which is what an "€X for Y%" offer implies. The pitch's `valuation` is the founder's asked **pre-money** valuation, matching the homework's "selling a startup at a €2M valuation". The calculator exposes both, so the UI can show "€500k for 30% values you at €1.17M pre-money".

Rounding: money to the nearest euro (`Math.round`), equity to 2 decimals. Equity is a JS number, so the "at most 2 decimals" check compares `x * 100` with its rounded value within `1e-9`, not `multipleOf(0.01)`, which fails on values like `0.29`.

*Alternative considered:* storing equity in basis points (integer). It's exact, but every API payload, prompt and UI slider would need converting; percentages with a 2-decimal rule are simpler for this game.

### 3. Turn input shape
`PlayTurnRequest` is a strict object with optional `optionId`, `offer` and `message`, plus a refinement requiring exactly one. The structured `offer` input is `{ investment, equity }` only: the server computes `impliedValuation`, so clients can't send an inconsistent one. A discriminated union (`{ kind: 'option', … }`) was considered, but it makes the free-text request noisier for the web client and the CLI.

### 4. Public contracts are strict allowlists
Every DTO schema in `GameDtos.ts` is `.strict()`. `InvestorPersona.toPublicDto()` copies the five public fields by name (it doesn't spread the definition and then remove the hidden fields). The hidden types (`InvestorState`, `PersonaDefinition`) are defined in `apps/api` only, so `packages/shared` and the web app can't import them. `InvestorMeters` carries `interestLevel: 'low' | 'medium' | 'high'`, `patienceHint: string` and `trustHint?: string`; the mapper from hidden numbers to hints (`MeterHintMapper`) belongs to the policy change.

### 5. Config additions
- `game`: `{ currency: 'EUR', maxTurns: 1–50, defaultValuation: Money, features: { phases, dueDiligence, dealTerms, hiddenFacts, marketEvents, debrief: boolean, eventChance: 0–1 } }`, strict.
- `llm.decision.minConfidence: 0–1`, next to `provider`. It's a property of how the game reads decisions, not of one backend. Laya and Jev compute confidence differently, so the value may need tuning per provider later. If that happens, it can move into `providers.<name>` without changing the spec's key name for the active provider.
- No new environment overrides: these are tuning values, not deployment settings.

The committed config gets `maxTurns: 15`, `defaultValuation: 2000000`, `minConfidence: 0.55` and all v2 flags `false` (`eventChance: 0.15`). `testConfig()` gets the same values.

### 6. Tables
All timestamps are `integer` ms (`mode: 'timestamp_ms'`), like `players`. JSON columns use `text({ mode: 'json' }).$type<T>()`. Repositories **parse JSON columns with their zod schema on read**, so a stored shape that drifts from the code fails loudly instead of leaking through untyped.

| Table | Columns | Keys / indexes |
| --- | --- | --- |
| `game_sessions` | `id` text PK (UUID), `player_id`, `persona_id`, `scenario_id` (nullable), `pitch` json, `status`, `phase`, `turn` int, `current_investor_offer` json nullable, `investor_state` json, `created_at`, `updated_at` | FK `player_id → players.id` (restrict); index `(player_id, created_at)` |
| `messages` | `id` text PK (UUID), `session_id`, `role`, `text`, `created_at` | FK → `game_sessions.id` on delete cascade; index `(session_id, created_at)` |
| `offers` | `id` text PK, `session_id`, `from`, `investment` int, `equity` real, `implied_valuation` int, `turn` int, `created_at` | FK cascade; index `(session_id, turn)` |
| `decision_logs` | `id` text PK, `session_id`, `turn`, `stage` (`A`/`B`/`debrief`), `provider`, `model` nullable, `questions` json, `answers` json nullable, `error_code` nullable, `latency_ms` int, `created_at` | FK cascade; index `(session_id, turn)` |

Ordering within the same millisecond uses SQLite's implicit `rowid` as a tie-breaker (`orderBy(createdAt, sql\`rowid\`)`). An autoincrement integer PK was considered, but UUIDs keep ids unguessable when they appear in URLs and DTOs later.

`terms` (offers) and the v2 tables are left out until the deal-terms change. Adding a nullable column later is a cheap, additive migration.

### 7. Repository surface
- `GameSessionRepository`: `create(session)`, `findForPlayer(id, playerId)`, `listForPlayer(playerId)` (newest first), `update(id, patch)` (status, phase, turn, currentInvestorOffer, investorState; always sets `updatedAt` from an injected `Clock`), `delete(id)`.
- `MessageRepository`: `add(message)`, `listForSession(sessionId)`.
- `OfferRepository`: `add(offer)`, `listForSession(sessionId)` (turn order), `latest(sessionId, from)`.
- `DecisionLogRepository`: `add(entry)`, `listForSession(sessionId)` (turn, then creation order).

There's no `findById` without a player id on the session repository. Ownership is enforced at the data layer, which is what the player-ownership requirement asks for. Repositories never hold business rules; the game engine composes them, and the multi-table writes for one turn will run inside a `db.transaction` there.

### 8. `ConfidenceGate`
`new ConfidenceGate(minConfidence)` with `assess(answer) → { uncertain: boolean; confidence: number }` and `assessAll(answers)`, which returns the same keys. Choice and score use the answer's `confidence`. Noul uses `max(p, 1 − p)`: a noul of 0.2 is a confident "no", and treating it as low-confidence would make the investor ask clarifying questions about clear judgments. The gate never mutates answers; the policy decides what "uncertain" means for its action.

### 9. `DecisionLogger`
`DecisionLogger.decide(context: { sessionId, turn, stage }, request)` calls `DecisionProvider.decide`, then writes the log row, and returns the provider's result or rethrows its error unchanged.
- On failure, the row has `answers: null`, `errorCode` = the `AppError` code (or `INTERNAL_ERROR`), `model: null`, and the latency measured by the logger.
- The repository write is wrapped in `try/catch`. A failed write is logged at `error` (with session, turn and stage, but no questions or answers) and swallowed.
- Several question sets in one stage are run by the caller as `Promise.all` over `decide` calls, one log row each, so the insights panel can show each set separately.

*Alternative considered:* a decorator that implements `DecisionProvider` and logs transparently. The session, turn and stage would have to reach it out-of-band (`AsyncLocalStorage` or a mutable field), which is implicit and easy to get wrong with parallel calls. An explicit context argument is clearer.

Rows store questions and answers only. The provider layer never puts keys in either, and the logger writes no request headers or config.

### 10. Personas
`PersonaDefinitionSchema` (API-only zod) validates each entry in `personaDefinitions.ts`, plus a refinement for `minEquity ≤ maxEquity`. `PersonaCatalog` is built in `Container`: it validates every definition, rejects duplicate ids and throws `PersonaDefinitionError` (a startup failure whose message names the persona id and field path). `PersonaCatalog` exposes `list()` (catalog order) and `findById(id)`.

The hidden numbers are chosen to satisfy the ordering requirements, and they're tunable later:

| id | budget | minEquity | maxEquity | initialInterest | patience | concessionStep |
| --- | --- | --- | --- | --- | --- | --- |
| `greedy-shark` | 600,000 | 22 | **40** | 0.5 | 5 | **1.5** |
| `generous-angel` | 900,000 | **8** | 20 | 0.7 | 4 | **5** |
| `angry-rude` | 500,000 | 18 | 30 | 0.4 | **2** | 3 |
| `content-well-fed` | 700,000 | 12 | 25 | 0.5 | **7** | 3 |
| `skeptical-analyst` | 650,000 | 15 | 28 | 0.35 | 4 | 2 |
| `impact-investor` | 750,000 | 10 | 22 | 0.55 | 5 | 4 |

Personalities, goals and tone instructions follow TASKS.md §8.2 (for example, the shark "wants a 2x liquidation preference" as a goal, which is harmless text until deal terms exist).

### 11. `GET /api/personas`
`PersonaController` (`basePath = '/personas'`) returns `PersonaListDto` with `Cache-Control: private, max-age=300`, since the catalog is static per deploy. It sits behind the standard middleware like every other feature controller. GET needs no CSRF token, and a player session is created as for any `/api` call. The Postman collection gains a "List personas" request.

## Risks / Trade-offs

- [Floating-point equity: `500000 / 0.15` ≠ exact] → All math goes through `ValuationCalculator` with explicit rounding, and the `Offer` refinement compares against the calculator's output, not a hand-written formula.
- [Hidden data leaking through a future DTO] → Strict DTO schemas, allowlist mapping, API-only hidden types, and a test that scans the `/api/personas` body for hidden keys and every persona's budget value. The game-engine change adds the same test for sessions.
- [The JSON column shape drifts from the code] → Zod parsing on read turns drift into a clear error at the repository instead of corrupt game state.
- [Decision logs grow without bound: questions are stored on every call] → Acceptable for a local homework game. Cascade delete on sessions gives a cleanup path later.
- [`minConfidence` doesn't transfer between Laya and Jev] → One global value for now (0.55); the Laya vs Jev comparison in the homework write-up will show whether a per-provider value is needed.
- [Persona numbers are guesses] → They're data in one file, guarded by the ordering tests from the spec, so tuning them doesn't touch logic.

## Migration Plan

1. Add the tables to `schema.ts`, then run `pnpm db:generate` to produce `0001_*.sql`, and review it: it must be `CREATE TABLE` / `CREATE INDEX` only.
2. `Database` applies it automatically on the next start. Existing `data/game.sqlite` files keep their players.
3. Rollback: Drizzle has no down migrations. To revert, drop the four tables by hand (`DROP TABLE decision_logs; offers; messages; game_sessions`) and delete the `0001` entry from `__drizzle_migrations`, or delete the local dev database file.
